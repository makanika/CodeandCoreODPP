## Direction: Build Complaints First

The next slice should build the **Type B complaints workflow**, because it is the core product purpose. Keep case information strictly contextual to a complaint; do not build a general case-management module.

1. Create the `complaints` models for complaint reference, PIN hash, contact preference, intake channel, classification, case-reference context, assignment, inquiry, determination, communication proof, and immutable timeline events.
2. Add the Type B routing state machine: `RECEIVED -> OPEN_RSA -> RESOLVED_RSA | ESCALATED_REGIONAL -> RESOLVED_REGIONAL | ESCALATED_HQ -> REINSTATED | SANCTIONED`, plus `WITHDRAWN` and `REFERRED_OUT` terminal paths.
3. Link Type B complaints to ordinary `documents.Document` records through an explicit complaint-document relation. Apply scope checks before a review, comment, attachment, or download is returned.
4. Build the public complaint intake and reference/PIN tracker. It must return only plain-language status and must not disclose case narrative, officers, attachments, locations, or internal timelines.
5. Build the restricted staff complaint desk, with assignment to the responsible RSA, escalation through the staff reporting/scope structure, and communication proof required before closure.
6. Only then create the separate `conduct` schema and database models for Type A handoff. Never add Type A narrative or evidence fields to the normal complaints or documents tables.

## Current Risk and Decision

The technical base is ready, but the action/scope matrix and final station-to-region mapping remain approval-dependent. Build the Type B workflow with controlled demo values and configuration points; do not hard-code unapproved operational mappings or public service commitments.
