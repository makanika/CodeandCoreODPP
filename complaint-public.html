02 — Execution checklist, as it stands today

What the blueprint asks for vs. what already exists

Read against complaints/models.py, views.py, services.py, and the templates.

Partial

Data model extension

NIN (complainant_nin) and a hashed PIN (tracking_pin_hash) already exist on Complaint. There is no stakeholder_role field and no stored QR image — the QR is generated on request, not persisted.

New

Stakeholder case lookup view

Doesn't exist yet. Would search CaseIdentifier by reference_type + value — the blueprint's flat fields (police_file_number, court_file_number, crb_number) aren't how the real CaseReference model stores identifiers.

New

Officer-guided ingestion view

Today's lodge_complaint is self-service only and hardcodes intake_channel='PUBLIC_PORTAL'. An assisted-desk path would reuse the same create_complaint() service with intake_channel='ASSISTED_DESK' and a passed-in captured_by officer — that channel enum already exists.

Exists, different design

Receipt & QR generation

qr_png() already renders a QR with the qrcode library. It's not stored as an ImageField — it's generated on the fly and inlined into the receipt as base64, and it encodes a signed opaque locator rather than a plain ?ref= URL.

Exists, different design

Nationwide verification portal

track_complaint + track.html already take reference + PIN and return plain-language status. It doesn't yet auto-populate from a scanned QR, because the QR doesn't carry the reference in cleartext (see reconciliation below).

03 — Reconciliation

Where the blueprint's code would conflict with what's shipped

Dropping the pasted snippets in as-is would break or duplicate existing behaviour.

Biggest one: the blueprint's generate_qr_code() encodes the plain reference in a public URL (?ref=CMP...). The brief's security boundary requires the QR locator to be opaque — the shipped design already does this correctly with a signed UUID locator, not a readable reference.

04 — Decisions needed before I write anything

Four questions the blueprint doesn't settle on its own

  • 1

    Is an officer-guided desk flow actually wanted as new scope? The brief already covers walk-in intake through the existing ASSISTED_DESK channel on the same form. A dedicated case-lookup-first screen is extra surface area — worth it only if desk officers need to search cases before a citizen states a reference.

  • 2

    Should stakeholder_role and NIN become mandatory? Right now NIN is optional and there's no role field. Making both required is a model + migration + form change, and affects the public form's friction.

  • 3

    Does the QR still need to stay opaque? The blueprint's plain ?ref= URL is simpler to implement but exposes a real complaint reference to anyone who photographs the receipt. Recommend keeping the signed-locator design already shipped.

  • 4

    Domain in the blueprint (odpp-complaints.codeandcore.dev) — is that the actual pilot host, or a placeholder from the blueprint author? It doesn't appear in core/settings.py yet.

05 — Recommended path, once we agree

Build only the gap, in the shipped style

If desk lookup is wanted

Add a case_lookup view searching CaseIdentifier__value, function-based, rendered with odpp-* classes — not a new design system.

If stakeholder capture is wanted

Migration adding stakeholder_role to Complaint; extend PublicComplaintForm; make NIN required only on the assisted-desk path, not the public one.

Everything else

No change — reference format, PIN hashing, QR opacity, and the tracking portal already satisfy the blueprint's intent through a different, brief-compliant implementation.
