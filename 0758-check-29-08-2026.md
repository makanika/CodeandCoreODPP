## Cases and Complaints Boundary

Keep the `cases` app, but give it a deliberately limited responsibility. It must not become a criminal case-management system.

`cases` should contain a minimal `CaseReference` and reference ledger for SD/OB, CRB, ODPP, and court identifiers; originating station; responsible region; and safe custody/status context. A Type B complaint can then link to one or more verified case references and use that context for RSA and regional routing. It must not add trial preparation, prosecution collaboration, court scheduling, or general case-file workflow.

## Direction: Build Case Context, Then Type B Complaints

1. Build the limited `cases.CaseReference` model and its normalised SD/OB, CRB, ODPP, and court reference entries. Link it to the existing `Office` hierarchy and staff custody context only where needed for a complaint.
2. Build the `complaints` core models: reference, hashed PIN, public contact preference, intake channel, linked case reference, classification, assignment, priority, SLA target, and append-only timeline events.
3. Implement the Type B state machine and complaint assignment. Resolve the accountable RSA from the linked case context and use the staff posting/reporting structure for regional and HQ escalation.
4. Connect Type B records to permitted `documents.Document` entries and logged-in-person comments. Keep document access bound to complaint scope and role.
5. Build the public complaint submission and reference/PIN tracker, returning only safe plain-language status.
6. Build the sealed Type A conduct schema only after the normal Type B workflow and its boundary tests are working.
